# Client check-in forms

Built on branch `feature/client-checkin-forms` (from `release/1.0.1`), 2026-10-28. **Not run on a real phone, and the database part is not applied yet.** This is the first feature that hands one person's health information to another person, so the privacy rules below are the heart of it.

## What it does
**Trainer side** (Shop tab > Trainer Tools > new **📝 Forms** segment; only people with a trainer profile see it)
* **Form:** a title, an optional introduction, switches for ten standard questions (body weight, energy, sleep, stress, soreness, training plan followed, nutrition plan followed, wins, struggles, questions for the coach), and up to **10 questions of their own**. Own questions come in five types: written answer, number (with a unit), scale (1 to 5 or 1 to 10), yes/no, pick one (2 to 8 options). One form per trainer, shared by all their linked clients.
* **Clients:** the trainer types a name (or picks one of the clients already in their tracker) and makes a **one-time invite code**. They send it to the client themselves. They see who is linked, who has not used their code yet, and who has stopped.
* **Inbox:** the check-ins clients send, newest first, with an unread count. Opening one marks it read. The trainer can write feedback that the client sees.

**Client side** (Profile > Account > **🤝 My coaching check-ins**; everyone sees it)
* **Join a trainer** by typing the code. See the trainers they are linked to, fill in the trainer's form, read the feedback, **stop sharing** at any time, delete any past check-in, and **report** the trainer (uses the existing trainer report).
* Before answering, the form says "This goes to {trainer} only. Every question is optional." Nothing is required.

## Privacy rules (all enforced in the database, `supabase/client_checkins.sql`, and tested)
* **Linking needs the client's own action.** A trainer cannot link a person by choosing them. The client must type a code the trainer made.
* **Codes:** 8 characters from a 32-character alphabet with no look-alikes (no I, O, 0, 1), generated by the database from a secure random source, **single use, expire after 7 days, stored only as a hash**. Wrong codes are counted: 8 an hour per person, then the person is stopped. A trainer cannot use their own code. At most 50 unused invites and 300 links per trainer.
* **The trainer never learns who the client is in the app.** They see only the name they typed. The client's account id is hidden from the trainer by column permissions, on links and on check-ins.
* **Answers go to one trainer.** Other trainers, other users and logged-out visitors cannot read them (tested). Clients do not read the tables directly; they use functions, so a person who is both a trainer and a client never gets the two mixed up.
* **Ending a link stops access on both sides.** When either side ends it, the trainer can no longer read that client's check-ins (past ones too), and nothing more can be sent. The client **keeps their copy** and can delete it. If the same person is linked again later, the trainer starts fresh and does not see the old ones.
* **Deleting an account** deletes its links and check-ins, whether it is the client's or the trainer's account.
* **Answers cannot be forged.** The client's check-in is saved by a database function that builds the question list itself from the trainer's current form, checks every answer's type and range, and refuses answers to questions that are not on the form, wrong types, out-of-range numbers, over-long text, and empty check-ins. At most 20 check-ins a day per link.
* **Old check-ins never change.** Each check-in stores a copy of the questions it answered, so later edits to the form do not alter how it reads.
* **No photos, no files.** Progress photos stay on the phone, as everywhere else in the app. There is no photo question type.

## Decisions I made (easy to change, tell me if you want them different)
* **Trainer loses access when a link ends**, even if the trainer is the one who ended it. This is the privacy-first choice. The alternative (trainer keeps what was sent while linked) is a small change but means a client cannot fully withdraw.
* **Nothing is required** in any form, so a trainer cannot force a sensitive answer.
* **One form per trainer** (not one per client). Different forms per client would be a later addition.
* **No notifications.** The app cannot send push notifications (that entitlement is stripped), so a trainer sees new check-ins when they open the Inbox, and a client sees feedback when they open My coaching check-ins. The trainer can nudge a client through the existing chat.
* **Trainer-written questions are user content.** Clients see them before answering, can skip them, can stop sharing and can report the trainer. The editor tells trainers not to ask for medical diagnoses, payment details or passwords. I cannot stop a trainer typing a bad question; the report path is the safeguard.
* **The trainer's private tracker (Clients and Check-ins tabs) is unchanged and not connected** to this. Check-ins received are not copied into it automatically.

2. **Privacy policy and App Privacy:** this is new. Suggested wording (review before publishing):
   > **Coaching check-ins.** If you choose to link with a trainer using an invite code, the answers you send in a check-in (for example weight, energy, sleep, stress and notes) are shared with that trainer only. You can stop sharing at any time, after which the trainer can no longer see them, and you can delete your check-ins. They are deleted when you delete your account.
   In App Store Connect > App Privacy, **Health and Fitness** and **User Content** should be declared as collected and linked to the user for App Functionality (check the existing answers already cover this), and the policy should say data can be shared with a trainer the user chooses.
3. **App Review notes for 1.0.1:** explain the invite-code flow and give reviewers a trainer demo login and a client demo login with a working code (or a pre-linked pair), otherwise they cannot see the feature. Mention that clients can stop sharing and report the trainer (Guideline 1.2).
4. **Look at it on two real phones (TestFlight):** a trainer makes a code; a client types it; the client sends a check-in; the trainer opens it and replies; the client sees the reply; the client stops sharing and the trainer's inbox empties.

## Known limits
* A client cannot see the form until a trainer has saved one ("has not set up a check-in form yet").
* Ended links stay in the trainer's list as history (the 300 limit counts only active and unused ones). There is no button to remove them from the list; deleting one would delete the client's copy too, so it is deliberately not offered.
* The standard questions exist in two places (`STANDARD_QUESTIONS` in `lib/checkinForms.ts` and `checkin_standard_catalog()` in the SQL). A test fails if they differ, so change both together.
* No charts or trends across a client's check-ins yet (for example weight over time). The data is there for it.
